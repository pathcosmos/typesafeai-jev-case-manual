# 02. 질문 설계

> 근거: [reference/02~07](../reference/README.md) · [reference/10](../reference/10-jaggedness.md) · [patterns/README 공통 설계 원칙](../patterns/README.md#공통-설계-원칙-쿡북-전반에서-반복됨)
> 확인일: 2026-09-24 · 기준: `jev-1.13.0`

## 설계 순서

1. **애플리케이션이 할 행동에서 출발한다.** 무엇을 보여주고, 고르고, 바꾸고, 넘기는지 적고, 그 행동에 필요한 판단을 역으로 도출한다.
2. **판단을 원자로 쪼갠다.** 판단 하나에 질문 하나를 둔다. "포함, 차단, 실행해도 되는가"를 직접 묻지 말고 그 결정을 가르는 속성들을 묻는다. 결정은 코드가 한다.
3. **질문마다 primitive를 고른다** ([reference/03 결정 흐름](../reference/03-primitives.md#유형-결정-흐름)).
4. **state를 설계한다.** 질문에 필요한 것만 넣고, 이름 붙은 필드와 백틱 경로를 쓴다.
5. **같은 state의 질문은 모두 한 요청에 넣는다.** 추측성 질문도 포함한다. 두 번째 요청은 진짜 의존성이 있을 때만 한다.
6. **질문과 임계값 상수를 한 모듈에 모은다.** 사람이 리뷰할 대상은 질문 문구와 임계값이다.

## 질문 설계 템플릿 (케이스 문서와 코드 리뷰에 사용)

| 항목 | 기입 |
| --- | --- |
| 질문 ID | `refund_requested` (코드용이며 모델은 보지 않는다) |
| 이 답을 쓰는 코드 경로 | 어느 분기, 어느 임계값에서 무엇을 하는가 |
| primitive | Choice / Score / Noul, 그리고 고른 이유 |
| instructions | 완전한 문장. state의 필드는 백틱 경로로 가리킨다 |
| criteria | 선택지와 설명 / 레벨 서술 / `true`·`false` 정의 |
| no-match 처리 | `other`/`none` 선택지 / 존재 여부 Noul / 해당 없음 |
| 추측성 여부 | 일부 입력에서만 쓰는지와 그 조건 |
| 임계값이 읽는 값 | confidence / p_top / noul / score ([catalog §0.2](../patterns/catalog.md#02-신호-종류-임계값이-무엇을-읽는지가-쿡북마다-다름)) |

## 체크리스트

### 판단 단위
- [ ] 질문 하나가 판단 하나인가? "and"나 "or"로 이어진 조건은 나눈다.
- [ ] 사람이 몇 초 안에 답할 수 있는 스냅 판단인가?
- [ ] 계산, 카운팅, 날짜 비교, 수치 보간이 섞여 있지 않은가? 섞여 있으면 코드로 옮기고, 코드가 계산한 값이나 **이름 붙은 구간**을 state에 넣는다.
- [ ] 자유 값을 생성하게 하지 않는가? 필요하면 후보를 만들어 Choice로 고르게 한다 (후보가 빠짐없이 들어갔는지 확인).
- [ ] 이중 부정이나 "속성의 속성" 같은 간접 참조가 없는가?

### 문구
- [ ] instructions만 읽어도 질문의 의미가 **완전한가**? ID는 모델에게 전달되지 않는다.
- [ ] 모델이 **문자 그대로** 읽어도 의도가 전달되는가? 틀린 답을 보고 "사실은…"이라고 설명하게 된다면, 그 설명을 instructions나 criteria에 넣는다.
- [ ] Noul은 **높은 값이 yes**가 되도록 썼는가? ("…이 없는가?"처럼 뒤집지 않는다)
- [ ] instructions와 criteria가 모순되지 않는가? (`true`가 no를 뜻하지 않는다)
- [ ] 결정을 가르는 **가장 좁은 사실**을 묻는가? 단어 하나가 결과를 바꾼다 (autoformat 사례: 17블록 vs 12블록).

### criteria
- [ ] Choice: 선택지 설명이 서로 **구분되는가**? 자주 헷갈리는 쌍에는 `what` / `not_for` / `examples`를 둔다.
- [ ] Choice: 목록이 모든 입력을 덮지 못하면 `other` / `none`을 넣었는가? (빼면 억지로 고르고, 커뮤니티 실험에서는 정확도가 붕괴했다)
- [ ] Choice: 선택지가 200개를 넘으면 계층화나 2-pass를 고려했는가? (한도 255, 한 쿡북은 "약 240까지 안정적"이라고 적음)
- [ ] Score: 레벨이 **정도가 아니라 상황**을 서술하는가? 각 레벨이 단독으로 의미가 통하는가? 숫자만 쓴 레벨은 없는가?
- [ ] Score: 2~10개이고, `null` 레벨이 없는가? (null이면 422, 11개 이상이면 400)
- [ ] Score: 한 차원만 재는가?
- [ ] Noul: criteria 없이 먼저 시험했고, 경계가 미묘할 때만 `true`/`false`를 추가했는가? (OpenRouter를 거친다면 둘 다 필수)
- [ ] 예시(examples)는 **실제 입력과 닮았는가**? 무관한 예시는 효과가 없다.

### state와 요청 구성
- [ ] 여러 부분이 있으면 object로 만들었는가? 질문이 참조하는 필드를 백틱 경로로 가리켰는가?
- [ ] 질문과 무관한 내용을 코드로 걸러 냈는가?
- [ ] 같은 state의 독립 질문을 **한 요청**에 모았는가? (에이전트가 가장 자주 틀리는 부분이다)
- [ ] 항목이 여러 개면 한 state에 몰아넣지 말고 **항목마다 질문**(또는 쌍마다 요청)을 두었는가?
- [ ] 비교형 판단(A vs B)은 순서를 바꿔 두 번 묻고 평균을 내는가? (위치 편향 대응. 두 질문을 한 요청에 넣는다)
- [ ] 사용자가 통제하는 텍스트가 state에 들어가는가? 그렇다면 adversarial 케이스를 평가셋에 넣는다.
- [ ] Choice 선택지 순서를 고정했는가? (순서 민감도에 대한 증거가 엇갈린다)

## 문구 개선 루프

1. 평가셋에서 틀린 사례를 모은다 ([04](04-evaluation.md)).
2. 원인을 분류한다: **state에 증거가 없음 / 문구가 모호함 / 선택지가 겹침 / 모델의 약점(jaggedness) / 코드 조합 오류**.
3. 문구를 고치거나, criteria를 대조형으로 바꾸거나, 질문을 분해하거나, 그 부분을 코드로 옮긴다.
4. 고친 뒤 **별도 테스트셋**으로 확인한다. confidence가 올랐다고 해서 좋아진 것은 아니다.
5. 기준 자체가 레이블링하면서 바뀌는 것은 정상이다 (criteria drift). 개정할 때마다 평가셋을 다시 돌린다.
