# 03. Primitives — 질문 유형 고르기와 공통 규칙

> 출처: [primitives](https://docs.typesafe.ai/primitives.md) · [introduction](https://docs.typesafe.ai/introduction.md)
> 확인일: 2026-09-24 · 기준: `jev-1.13.0`

## 세 가지 유형

| 유형 | 답하는 질문 | 반환 | 코드에서의 대응 |
| --- | --- | --- | --- |
| [Choice](04-choice.md) | 이 선택지들 중 무엇인가? (순서 없음) | `choice`, `probabilities`, `confidence` | `switch` / N개 코드 경로 |
| [Score](05-score.md) | 어느 레벨인가? (순서 있는 스펙트럼) | `score`, `legend`, `probabilities`, `confidence` | 임계값, 정렬 |
| [Noul](06-noul.md) | 이것은 참인가? | `noul` (yes일 확률 0~1). **confidence 없음** | `if` |

## 유형 결정 흐름

```
답이 예/아니오인가?
 ├─ 예 → 조건을 명확히 정의할 수 있는가? ── 예 → Noul
 │                                  └─ 아니오("강한가?" 같은 정도 문제) → Score
 └─ 아니오 → 선택지 사이에 순서가 있는가?
          ├─ 있음, 각 단계를 상황으로 서술할 수 있음 → Score
          └─ 없음 → Choice (목록이 모든 입력을 덮지 못하면 other / none 추가)
여러 라벨이 동시에 해당할 수 있는가? → 라벨마다 Noul
```

- 두 유형이 모두 맞아 보이면 **코드가 바로 행동으로 옮길 수 있는 쪽**을 고른다.
- ⚠️ **Noul 0.5는 "중간 정도"라는 뜻이 아니다.** yes와 no의 확률이 비슷하다는 뜻이다. 정도를 측정하려면 Score를 쓴다.

## 질문 정의 (모든 유형 공통)

| 필드 | 설명 |
| --- | --- |
| ID (map의 key) | 코드용 식별자. **모델에게 전달되지 않는다.** 따라서 질문의 의미는 전부 `instructions`에 써야 한다. |
| `type` | `choice` / `score` / `noul` |
| `instructions` | 질문 또는 판단할 진술. string, object, array 모두 가능 ([07](07-structured-questions.md)) |
| `criteria` | Choice: `{option: description \| null}` map. Score: 순서 있는 레벨 배열. Noul: 선택 사항 `{true, false}` |

## 답의 두 가지 성질 (조합 가능성의 근거)

1. **항상 주어진 선택지나 레벨 안에서만 답한다.** 목록 밖의 값을 지어내지 않는다. 산문을 파싱할 필요가 없다.
2. **각 답은 독립적이다.** 한 질문의 답이 다른 질문의 숨은 맥락이 되지 않는다. 질문을 추가하거나 빼도 다른 질문의 결과는 바뀌지 않는다.

## 규칙 1: 질문 하나에 스냅 판단 하나

- 좋은 질문: "Does this message convey urgency?"
- 나쁜 질문: "Analyze this message and determine the best course of action" → 느린 추론이 필요하므로 **분해하라는 신호**다.
- 여러 요인에 달린 판단은 요인별로 질문하고 코드에서 가중치로 합친다 (예: 피치 평가 → 시장 규모, 기술 실현성, 차별성). 우선순위가 바뀌면 프롬프트가 아니라 **계수를 바꾼다**.

## 규칙 2: 같은 state에 대한 질문은 한 요청에 모은다 (fan-out)

- 병렬로 평가되므로 질문을 추가해도 **응답 시간이 거의 늘지 않는다.** 비용은 추가 질문의 토큰만큼만 든다.
- **추측성(speculative) 질문**도 함께 넣는다. 일부 입력에서만 의미 있는 질문(예: 버그일 때만 쓰는 severity)도 묻고, 필요 없는 답은 코드가 무시한다.
- 공식 cookbook의 예시 결과(`jev-1.12`): 13개 질문을 한 번에 보내는 것이 따로 보내는 것보다 **12.2배 싸고 10.0배 빨랐다.** 답의 차이는 noise 범위 안이었다. 단, 10.0배는 13번의 단일 호출을 **순차로 합산**한 기준이다. 동시에 호출하면 속도 격차는 줄지만, state 토큰을 반복해서 내는 비용은 그대로다 ([sources D3](../sources.md#불일치--미확인-항목)).
- 공식 팁: 코딩 에이전트는 **"한 호출에 질문 하나"라는 습관에 사람보다 더 쉽게 빠진다.** 리뷰할 때 반드시 확인한다.

## 규칙 3: 두 번째 요청은 진짜 의존성이 있을 때만

진짜 의존성이란 **앞 답이 없으면 다음 요청을 만들 수 없는 경우**다:
- 앞 답을 보고 state에 넣을 데이터를 추가로 가져와야 할 때 (예: skill_suggestion은 상위 3개의 본문을 가져와서 다시 판단한다)
- 앞 답이 state의 구성 자체를 결정할 때 (예: autoformat은 줄 병합 결과로 블록을 만든 뒤 분류한다)
- 앞 답이 다음 질문의 선택지를 결정할 때 (예: 계층 분류에서 하위 노드를 선택지로 쓴다)

그 외에는 원래 state로 물을 수 있는 질문이므로 **첫 요청에 넣고 코드에서 무시**한다.

## 답 읽기 요약

| 유형 | 읽는 법 |
| --- | --- |
| Choice | `choice`는 최고 확률 선택지. `probabilities`의 합은 1. `confidence`는 분포가 얼마나 뾰족한지를 나타낸다 |
| Score | `score`는 레벨 번호의 확률 가중 평균이라 레벨 사이 값이 나올 수 있다. 같은 score도 분포는 다를 수 있으니 `probabilities`를 함께 본다 |
| Noul | 1에 가까우면 강한 yes, 0에 가까우면 강한 no, 0.5 근처면 불확실. 이 값 자체가 답이자 확신도다 |
