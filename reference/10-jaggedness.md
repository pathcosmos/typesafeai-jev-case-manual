# 10. jev-1.13 약점 (Jaggedness)

> 출처: [model-jaggedness/jev-1.13](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md) (공식 last reviewed 2026-09-17)
> 확인일: 2026-09-24 · 기준: `jev-1.13.0` · **다음 버전에서 많은 항목이 고쳐질 예정이라고 공식 문서가 밝혔다. 버전이 바뀌면 다시 확인한다.**

jev-1.13은 System One 작업(상식적인 스냅 판단)에서 가장 잘한다. **여러 단계의 간접 참조, 문자 그대로의 해석, 수치 정밀도**에 약하다.

## 9가지 실패 모드와 우회법

| # | 실패 모드 | 증상 | 이렇게 한다 |
| --- | --- | --- | --- |
| 1 | **Literal reading** | 의도가 아니라 **쓰인 단어 그대로** 답한다. 범위를 한정하는 단어, 부정, 암묵적 조건을 액면 그대로 읽는다 | 정확한 조건을 instructions에 쓰고, 경계 사례는 criteria에 넣는다. *틀린 답을 보고 "사실 내 뜻은…"이라고 설명하게 된다면, 그 설명이 instructions에서 빠진 절반이다.* 해석이 불가피하면 문자 그대로의 질문 두 개로 나눈다 |
| 2 | **Math & numbers** | 계산, **카운팅**(글자 수, 등장 횟수, 긴 목록의 항목 수), 숫자 표현(hex 색상, RGB, 어셈블리)에 약하다 | 산술은 코드에서 한다. 카운팅은 **항목마다 Noul을 묻고 코드에서 합산**한다. 숫자는 코드에서 변환해서 계산된 값이나 **이름 붙은 구간**으로 넘긴다 |
| 2b | Score로 수치 보간 | 레벨 사이의 score로 정확한 크기를 복원하려 한다 | score는 임계값 판정에만 쓴다. 레벨의 수치적 보정이 약하다 |
| 3 | <a id="date-time"></a>**Date/time 비교** | 날짜를 순서 있는 양이 아니라 텍스트로 읽는다. 전후 관계, 간격, 기간 포함 여부를 신뢰할 수 없다 (형식이 섞이거나, 상대 표현이거나, 분기나 정산 기간 경계에서 더 나빠진다) | **추출은 모델이, 계산은 코드가** 한다. 연, 월, 일을 각각 닫힌 집합의 Choice로 묻고 "not stated" 선택지를 넣는다. 조립, 정렬, 기간 계산은 코드에서 한다 (cookbook: date_extraction) |
| 4 | **Indirection** | 이중 부정이나 "속성의 속성"처럼 여러 단계를 거치는 질문에서 정확도가 떨어진다 | 최대한 직접적으로 쓴다. state의 관련 부분을 **이름(백틱 경로)으로 지정**한다 |
| 5 | **큰 state + 무관한 내용** | distractor 때문에 정확도가 떨어지고, 원인을 추적하기도 어려워진다 | 코드에서 먼저 검색하고 필터링한다. 필요한 필드만 보낸다. 필터링이 어려우면 Noul로 관련성을 먼저 거른다 |
| 6 | **Adversarial content** | state를 적대적인 입력으로 보지 않는다. 주입된 지시, 오도하는 프레이밍, 스스로의 분류를 주장하는 텍스트에 답이 흔들린다 | criteria를 명시적으로 쓴다. 배포 전에 edge case를 충분히 테스트한다. 사용자 입력을 state로 넣는 경우라면 **이 한계를 전제로 설계한다** |
| 7 | **Contradictory instructions/criteria** | instructions와 criteria가 서로 다른 것을 요구하면 혼란스러워한다. 예: `true`가 no를 뜻하는 Noul | criteria를 instruction의 연장으로 쓴다. 보통 사람이 읽고 바로 이해할 수 있게 쓴다 |
| 8 | <a id="structural-invariants"></a>**Structural invariants** | 의미가 비슷한 입력에는 매우 일관되게 답하지만, 사람이 기대하는 구조적 항등식은 보장하지 않는다. 같은 질문을 Noul(0.22)과 Choice(yes 0.01)로 물으면 값이 다르다. Noul(refund) 0.72 + Noul(not refund) 0.47 = 1.19 | 원하는 의미를 **직접** 묻는다. Noul에서 튜닝한 임계값을 Choice로 옮기지 않는다. 별개의 질문 사이에 산술 항등식을 기대하지 않는다. Choice는 상대적(어느 것), 선택지별 Noul은 절대적(각각 해당하는지)이다 |
| 9 | <a id="generation"></a>**Generation** | 텍스트 생성용으로 학습되지 않았다. Choice를 연쇄해서 억지로 생성하면 품질이 나쁘고 매우 느리다 | 추출할 때는 정규식이나 생성 모델로 **후보를 만들고** Jev는 **선택만** 한다. 텍스트 생성이 필요하면 다른 모델을 쓴다 |

## 피해야 할 것 (공식 요약)

- 코드로 정확히 계산할 수 있는 것을 모델에게 묻는 것
- 한 질문에 판단 여러 개를 숨기는 것
- System Two 작업 (간접 참조가 여러 겹인 것)
- 질문에 필요한 것보다 많은 맥락을 state에 넣는 것 (Jev는 context rot을 겪는다)

## 설계 리뷰 체크리스트

- [ ] 질문 중에 계산, 카운팅, 날짜 비교가 있는가 → 코드로 옮긴다
- [ ] "and"로 이어진 조건이 있는가 → 질문을 나눈다
- [ ] 부정형이나 이중 부정이 있는가 → 긍정형으로 바꾼다
- [ ] 자유 형식 값을 생성하게 하는가 → 후보를 뽑고 Choice로 선택하게 한다
- [ ] state에 질문과 무관한 큰 덩어리가 있는가 → 필터링한다
- [ ] 사용자가 통제하는 텍스트가 state에 들어가는가 → adversarial 케이스를 테스트 세트에 넣는다
- [ ] 서로 다른 질문 사이에 산술 관계를 가정하는가 → 제거한다
